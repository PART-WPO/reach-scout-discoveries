# REACH Scout targeted metadata recovery and human-intake policy (2026-10-30)

The research and reviewer workflows are **separate gates**. A missing field does not prove an item is ineligible, but neither does a credible grant/project connection prove that it is a unique catalogable output. Preserve all original DOI dispositions, Hub decisions and existing 24-column Discovery Hub CSV contract.

## Step 0 — output eligibility before metadata
For each DOI/URL separately verify: public standalone output identity; actual specific WPO project bridge (direct output-level award evidence, or qualified independent SPARK-linked association with clear uncertainty); candidate type; dates/creators where known; existing REACH and Scout duplicate/version-family checks and private reviewer decisions when available. Broad NOAA CI awards, author/topic overlap and inaccessible repository pages by themselves do not prove WPO funding or uniqueness.

## Targeted recovery by missing field
- **Dataset release/publication date**: Inspect native repository landing and API (e.g., DesignSafe, Dryad, Figshare, Zenodo, Scripps ERDDAP, HydroShare, Dataverse), repository version-history provenance, DataCite `dates.dateType` and recorded created/published/available date type, primary paper data availability and project data catalog. Never substitute paper year, DOI registration, dataset observation period, conference date, report submission or last-modified timestamp for FIRST public release.
- **Software initial release**: GitHub/GitLab release/tag provenance, README version notes, Zenodo archived releases and concept/version relations. Distinguish release dates from source revisions.
- **Poster, conference abstract, technical report**: Official conference program and first publicly posted archive version, repository issue/publication date, report series record and author-hosted copy. A presentation/submission date is not proof of public availability.
- **Duplicate/version/canonical identity**: exact DOI and URL, DataCite `relatedIdentifiers` relationship type, Zenodo concept/version chain, Figshare canonical version/identifier, repository record ID, file inventory and differences, public REACH record UID and known staged human dispositions. Group probable families for ONE human decision **without presuming duplicate identity**.
- **Public scope/access**: native files and download/permission state, accessible public abstract vs restricted participant data, selected project components; never treat closed datasets as publicly retrievable data, or publish sensitive files.
- **Award bridge**: direct output acknowledgement/publisher funding, official repository funding metadata, specific funded SPARK primary project output list, independent corroboration. Broad CI award alone insufficient.

## Recovery budget, evidence and stopping
Use source-aware checks rather than repeating the same generic search. Capture each distinct method, URL, source date type and result, conflicts, source failures, verified fields and remaining questions. Run an initial pass and ONE bounded diverse-source follow-up (normally <=5 new substantive checks), with a documented exception only for genuinely material new evidence. If a source is blocked, record **access failure**, not 'metadata does not exist'. Keep meaningful leads for human intake; do not continue indefinitely on required metadata that may not be published.

## Status and human workflow
1. `RESEARCH_ACTIVE`: meaningful unused sources remain.
2. `RESEARCH_COMPLETE_VERIFIED`: complete eligibility + required fields -> standard unique reviewed 24-column candidate.
3. `RESEARCH_COMPLETE_HUMAN_INTAKE`: credible project/output with unresolved date, version, distinctness or public scope -> **separate private intake queue**, with evidence and explicit review question. It is NOT a candidate published in Scout discovery batches, a Hub-verified imported card, an approval, nor public REACH.
4. `RESEARCH_COMPLETE_NO_ACTION`: evidenced duplicate, non-output, or insufficient project attribution -> preserve negative evidence; no proposal.
5. `HUMAN_REVIEWED`: reviewer records Needs Investigation / On Hold / Approved for Addition subject to final validation / Rejected or Already in REACH; do not infer approval, overwrite decisions or auto-publish.

The 37 pending_hub_handoff source cases from 2026-10-30 are grouped as **31 human decision units** in [metadata-review-units.json](metadata-review-units.json); six groups are provisional Zenodo/Figshare concept-version or Scripps alternate identity pairs and may or may not correspond to single outputs. All original 37 DOI/URL identities remain traceable, no automatic merge/reject has occurred. No Hub ingestion is claimed.

## Integration gate and safety
Existing 24-column Discovery Hub batch format stays unchanged. A proposed *additive private Apps Script review intake* may read the public [metadata-review-units.json](metadata-review-units.json) and present these in an independent review sheet/modal without writing existing Cases, decisions, REACH/SPARK/Smartsheet or staging CSVs. DO NOT claim this is installed or Hub-visible without observing a real authorized test/import in the bound spreadsheet. No publication date invention. Publishing to REACH still requires original destination schema validation; a reviewer may waive a missing field only where source policy/schema expressly permits it. Deployment requires the current Apps Script Hub source/version compatibility check and a controlled smoke test with a backup.

## Report independently
Count source cases; distinct review units; research-complete unresolved; private human intake installed and successfully imported (only with evidence); human-reviewed; verified approved; staged Hub candidates; verified public REACH additions, separately. An unresolved date and an unresolved identity are not the same type of blocker. Do not conflate counts.

## DataCite date reconciliation: source-first and no fabricated day (2026-10-30)

Every historical or new monthly DataCite-based Scout investigation must read the **original checksum-verified API intake row** first, retaining its title, type, creators, award(s), WPO program, parent project and abstract. Those fields must not be presented to a human as missing if they were already in the intake. Next read the independently refreshed read-only evidence in `api-discoveries/date-audits/historical-2026-10-28.json` or `api-discoveries/date-audits/monthly-YYYY-MM.json`, when published. The corresponding workbook lives in `api-discoveries/reports/REACH_DataCite_Date_Reconciliation_*.xlsx`.

The date evidence classifier keeps DataCite `dates[Issued]`, `dates[Available]`, `published`/`publicationYear`, `created` (DOI RECORD creation), `registered` (DOI registration), `updated` (metadata revision) and any DOI-identified native repository publication date **separate**. An exact machine-readable native publication date attached to the **same DOI** is more probative than a DOI registration timestamp, but still check concept/version and whether the item is a distinct first public release. A DataCite exact Issued or Available date without repository corroboration is a suggested candidate for review, not an automatic full REACH publication date; conflicting Issued vs Available dates are flagged rather than silently resolved. A year-only `published=2025` remains 2025, NEVER `2025-01-01`. The date of an API metadata update is not a public release date.

DataCite's official definition says `created` is when the DOI record entered DataCite; `registered` is registration with the global Handle system; `published` is a typed Issued date or falls back to publicationYear. These fields can align with repository publication but **cannot prove it in every case**. Native repository access failures must be recorded transparently. Do not use a timestamp from a parent resource as proof for a separately citable component, and keep DOI version/duplicate uncertainty distinct from missing-date uncertainty. When the automatic date audit produces a strong candidate or verified native date, bring that evidence to Scout/human reviewers; do not rewrite the public REACH Pub Date, original API CSV, or any private Hub decision automatically.

The date audit is conducted by the public GitHub Actions workflow `.github/workflows/datacite-date-reconciliation.yml`; the reports are replaceable evidence snapshots and are **not** Hub-ingestion files. The workflow runs on historical/monthly manifest changes, weekly, and on the first of the month following intake. No token or paid API worker is needed.

## REACH publication-date preparation default (executive decision, 2026-10-30)

The WPO reviewer elected to use **the calendar day from DataCite `created` as the default pre-filled REACH `Pub Date`** for DataCite DOI candidates. This is an operational convenience and an explicit office-level policy, **not** a statement that DataCite `created` means first public publication. It is the DOI metadata-record creation timestamp. Label the value **"DataCite created — editable default"**, retain the full original ISO timestamp and DOI-specific HTTPS source link, and let the human reviewer **change or clear the date** during preparation of a new REACH output. Save any overridden date, reviewer identity, date basis and evidence. Preserve a separate native-issued/available/full-publication date when available so the reviewer can choose it; never overwrite a human verified date with an API default.

Apply the default to **historical and monthly DataCite candidates**, including those still being reviewed for missing metadata. The default comes from the DOI's actual DataCite `created` value; never use a date from a related concept DOI, another version, an award, a parent dataset, an API `updated` timestamp, or an observation period. For a grouped version/alternate-identity review, choose the **canonical DOI first** before pre-filling that DOI's created date. A missing, unparsable or partial `created` date yields a blank default with an explicit reason. Do not invent `01-01` from a year.

Retain all existing *source data and research classifications* in the date audit. Surface both `verified_date` and `default_pub_date`; they may differ and must not be conflated. A default does not decide uniqueness, funding attribution, version relationship, or approval. The reviewer's final selected Pub Date may be inserted only through the existing authorized Discovery Hub/Smartsheet publication process and its validation; the separate metadata handoff review does **not** publish anything automatically. Existing privately reviewed candidates and historical immutable CSVs must not be rewritten. This office choice supersedes **only** older instructions that prevented a DataCite-created date from being offered as a **pre-filled preparation default**; it does not retroactively make that date verified publication evidence, and does not expand automatic approval or publication permissions.

When the full Google Apps Script Discovery Hub update is deployed, the "Add Missing Metadata" editor should display the date pre-filled with **DataCite created**, accompanied by an explicit source note and a simple editable field. No separate reviewer window. A manually verified date takes precedence over a provisional default.

## SUPERSEDING EXECUTIVE RULE — DataCite `created` COMPLETES the REACH Pub Date (2026-10-30)

This is the final, authoritative WPO data-entry policy. For any DataCite-backed DOI with a valid full `created` timestamp, **set REACH `Publication Date` / `Pub Date` to its calendar day `YYYY-MM-DD`**. The date is **complete and accepted for the office's cataloging purposes**. Do **not** mark Pub Date missing, blocked, pending verification, needing an evidence URL, needing a separately recorded reviewer decision, or requiring follow-up **solely** because `created` is not a historically proven first-public-release date. The office knowingly accepts that approximation. Do not require a user to click Save Pub Date, submit a date note, acknowledge date uncertainty, or manually verify the date to move forward with the normal new-output workflow. Reviewers retain a normal optional right to edit Pub Date during REACH insertion. Keep source provenance quietly (DOI, DataCite `created`, source link); an optional *Suggested Pub Date* line may say it came from DataCite. Do not repeatedly warn or raise a metadata-error badge about this choice.

**Separate concerns:** a valid created date resolves only the Pub Date field. Unknown output identity, duplicate/version-family relationships, eligibility, inaccessible public files, conflicting funding/parent project and genuinely absent *other* required metadata remain in Scout's normal finding/Needs Investigation pipeline. Never make a potentially duplicate item a confirmed new output solely by having a date. An item flagged `DATE_ONLY` whose sole actual missing field was the date MUST leave the **Human metadata needed** bucket after its valid DataCite created date is applied. Route it to ordinary **Potential new output / normal reviewer eligibility and duplicate review**, without auto-approval or automatic Smartsheet insertion. Mixed cases must **remove the date from the list of remaining gaps** but retain every other genuine gap and human decision. Preserve the original detailed research/history for audits, but count only remaining unresolved non-date issues in Hub badges, the hourly queue, and the 8 AM briefing.

For outputs with **no DataCite record/created date** (e.g. URL-only posters or reports) or malformed `created`, this shortcut does not apply and genuine date gaps can remain, subject to existing human exception rules. For DOI concept/version families, the correct specific DOI must be selected before assigning the date, and original identities remain traceable. For historical immutable CSVs, don't rewrite original ingestion or private human decisions; carry the effective Pub Date forward into a new derived/suggested-data view or staged candidate, with its actual authoritative source. Date-evidence audits may retain differences for research transparency, but a difference is **not** a REACH missing-Pub-Date blocker under this chosen policy.

This section **overrides any older rule** requiring independent native-repository corroboration, provisional-date confirmation, or a date-only Human metadata needed handoff for DataCite-created Pub Date. It does not change research evidence classification, deduplication, public output eligibility, publication controls or the rule that only an authorized human can approve a new addition.

## Mandatory direct DOI metadata enrichment for Scout-discovered related outputs (2026-10-30)

**This gate applies to ALL discovered DOI candidates, including independent award-by-award research, paper data-availability leads, related-output expansion, datasets and instruments, code, and outputs missing structured grant metadata.** An item discovered outside the original DataCite/Crossref award-number query is NOT exempt from a direct DOI lookup. Run the following **before** declaring its title, creators, type, abstract, accepted REACH Pub Date, or source metadata "missing", or escalating to Human metadata needed.

1. Extract and normalize the **exact output DOI** from the landing page, publisher citation, data availability statement or related identifier. Preserve version-vs-concept DOI and record identity; avoid substituting seed/paper DOI or parent DOI for the candidate.
2. For every valid DOI, query the **public, free** DataCite REST endpoint `https://api.datacite.org/dois/{normalized-doi}` directly (case-insensitive). This is an **identity lookup**, unlike the original award-number discovery search: **do not require** populated DataCite `fundingReferences` for a found DOI to be enriched. Check response DOI matches the intended candidate. If DataCite has no record (for example a Crossref-owned DOI), check the exact DOI in `https://api.crossref.org/works/{normalized-doi}`, and then the native repository/publisher if available. Respect HTTP rate limits, access failures and bounded retries; never infer a field is absent from an inaccessible API.
3. Retain title (including alternative titles if pertinent), creators, publisher, `types.resourceTypeGeneral`, version and relationships, abstract/description, `created`, `registered`, typed dates, `published` and year, rights/access metadata, and available file format/size indicators. Include DOI-specific DataCite/Crossref source URL and checked timestamp in the evidence trail. **For an exact DataCite DOI with valid full `created`, REACH Pub Date is automatically satisfied by its YYYY-MM-DD calendar date under the user's office policy**; do NOT flag it as missing or ask the human to verify that date. Retain `registered` separately; it does NOT override `created`. Reviewer may edit normal Pub Date if desired.
4. For `resourceTypeGeneral: Dataset` or an independently described dataset/interview/survey instrument, propose REACH Output Type **3 — Data & Instruments**. For Software, propose 2 — Code; for non-datasets classify according to the existing office output-type policy. A structured type is classification evidence, not proof of output independence or public file access. Rights marked open access, file formats/sizes and download metrics are helpful **access indicators**, but alone do not independently prove each file is downloadable. A publisher data-availability statement and an accessible DOI landing page can support normal reviewer eligibility without endless repeated anti-bot requests.
5. **Check funding two ways:** structured `fundingReferences` AND title/description/abstract for an exact WPO NOAA award and specifically funded project. An empty structured array is NOT evidence of no funding. Corroborate a textual award with SPARK project/award and independent publisher evidence where available. Record how funding was found and the certainty, rather than incorrectly labeling a DOI an original direct-award DataCite API match.
6. Combine the successful DOI lookup with the existing REACH and Scout dedup/version check. For the **normal Discovery Hub Potential new output** card, supply the known title, NOAA award, proposed parent, output type, author, Pub Date and evidence, and list **only genuinely outstanding questions**, such as version-family, distinctness, restricted files, or insufficient project attribution. The complete candidate continues through the existing **Scout Findings / Scout Recommendation / Scout Confidence** and human Approve/Needs Investigation/Reject actions; do not create a separate workflow. Never invent data, overwrite existing human edits, bypass reviewer decisions or auto-publish.

## Mandatory Crossref publication DOI metadata checkpoint (2026-10-30)

**Apply the same source-first DOI enrichment gate to journal articles, preprints, conference proceedings and other scholarly publications found by Scout, regardless of whether they originated from a monthly Crossref award-number API harvest, from historical award research, or from related-output expansion.** After normalizing the exact newly found DOI, look up its identity directly at `https://api.crossref.org/works/{DOI}`. A publication discovered through Scout's external research does not need to contain an award in Crossref's structured `funder[].award` list to be eligible for metadata lookup. If that DOI belongs to DataCite instead, use the DataCite branch. Rate limits (Crossref HTTP 429) trigger bounded polite retries or successful cached-source reuse, not a "no metadata found" conclusion.

Extract and preserve: complete title and subtitle where available, ordered creators (and ORCIDs if present), journal/container title, publisher, volume/issue/pages, `type` (propose REACH Output Type 1 for standard journal articles), abstract (if deposited), funder names and funding award numbers, DOI URL, related/updated content, and publication date history. **For Crossref publications, prioritize a full `published-online` date, then `published-print`, `published`, `issued`; for posted preprints use `posted` first.** Retain each source date and its precision; year-only or month-only fields must never be expanded to an invented calendar day. A complete date can supply an otherwise missing Pub Date for an ordinary Scout proposal, subject to the existing authorized reviewer workflow. Crossref `created` represents DOI registration and **must NOT automatically be substituted** for REACH Pub Date; that explicit office shortcut applies **only** to DataCite `created`. A disagreement between Crossref's published date and an existing human-reviewed date is an informational source comparison, not permission to overwrite the reviewer.

An absent Crossref abstract is not proof the publication has no abstract: check the journal/publisher article page before a truthful remaining-abstract escalation. Inspect both structured Crossref funding and publisher acknowledgments; empty `funder` entries do not negate output-level evidence from the paper or a confirmed SPARK project connection. Continue deduplication against full REACH and prior Scout findings and do not invent funding, a parent project or a distinct version. Show known fields in the normal Discovery Hub reviewer card and route only genuine remaining non-date issues to Human metadata needed/Needs Investigation.

They compare Crossref exact-DOI metadata to the existing Scout rows and report recovered titles/authors/abstracts/dates, full versus partial dates, and date conflicts **without modifying any original CSV, private human decision, Smartsheet record or public REACH output**. Monthly future DOI discoveries and later independently sourced publications enter this same deduplicated audit. The existing provenance attribution to Scout's related-output expansion is preserved even when Crossref was used after Scout discovered the DOI.
